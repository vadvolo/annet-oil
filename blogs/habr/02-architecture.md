# Внутри Annet Oil: четыре слоя, один хостнейм и решение про Docker Exec

В [первой статье](./01-introduction.md) я описал, *что* такое Annet Oil: единая
входная дверь перед парком контейнеров [annet](https://github.com/annetutil/annet),
доступная как CLI, REST API и MCP-сервер. Этот пост — про то, *как* он устроен.
А точнее — про два архитектурных решения, которые в итоге оказались важнее всего
остального.

<cut>

## Общая картина

```
AI-агент ──MCP──> mcp-annet-oil (Node) ──HTTP──> Annet Oil API (Go, :8080)
                                                       │
CLI (annet-oil) ──────────────────────────────────────┤
                                                       ├─ Docker Exec ─> annet-контейнеры
                                                       ├─ gNETcli ─────> show/exec на устройстве
                                                       └─ прямой TCP/SSH > check доступности
```

Слева входят три вещи: AI-агент (через MCP), человек (через CLI), пайплайн (через
HTTP). Все они сходятся в одном Go-ядре. Дальше ядро расходится на три вида работы
вниз: запуск annet внутри контейнеров, выполнение show/диагностических команд на
живых устройствах через gNETcli и прямой прозвон устройств для проверок
доступности.

Ключевое свойство: **интерфейс, через который вы вошли, не меняет того, что делает
ядро.** CLI и API — это тонкие оболочки над одними и теми же сервисными объектами.

## Решение №1: каждая фича — это одни и те же четыре слоя

Самое важное архитектурное правило в Annet Oil — не диаграмма, а соглашение.
Каждая фича, от `diff` до `check` и `featureset`, построена как **четыре слоя**, и
это всегда одни и те же четыре слоя:

1. **Ядро логики** — чистый Go-пакет в `internal/<feature>/`. Ни HTTP, ни Cobra,
   ни Docker. Только типы и функции, которые юнит-тестируются в изоляции.
2. **REST-хендлер** — `internal/api/handlers/<feature>.go` отдаёт ядро по HTTP и
   монтируется в `server.go`.
3. **CLI-команда** — `internal/cli/<feature>.go` заворачивает то же ядро в
   Cobra-команду.
4. **MCP-инструмент** — запись в Node/TypeScript MCP-сервере, которая дёргает
   REST-хендлер, чтобы фича досталась и агенту.

Возьмём проверку доступности устройства как эталонную реализацию. Чистая логика
(TCP-проба + попытка SSH-логина плюс batch-раннер) живёт в `internal/check/`. Она
ничего не знает о том, как её вызвали. Дальше:

```bash
# Слой 3 (CLI): прозвонить весь инвентарь параллельно
annet-oil check --concurrency 100 -o availability-report.json

# Слой 2 (REST): то же ядро, по HTTP
curl -X POST http://localhost:8080/api/v0/check \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"host": "10.0.0.1", "ports": [22, 23, 10022], "login": true}'
```

Оба пути вызывают идентичный код `internal/check`. CLI добавляет разбор флагов;
хендлер — маршалинг JSON и аутентификацию. Ни тот, ни другой не переписывают
логику. Когда я добавляю фичу, я не решаю, *как* её структурировать — соглашение
уже решило за меня. В этом и польза соглашения: оно убирает целый класс решений,
чтобы вы тратили здравый смысл на саму задачу.

Приятный побочный эффект: результаты несут **структурированные ошибки** — типовой
`Error{Type, Message}` с именованными константами вместо голых строк, — так что
любой потребитель, включая агента, ветвится по *типу* ошибки, а не по
string-match'у сообщения.

## Решение №2: маршрутизация по хостнейму — настоящая работа ядра

annet ничего не знает про вашу топологию контейнеров. У вас может крутиться:

- `annet-default` для основной массы современного железа,
- `annet-telnet` для легаси, которое умеет только telnet,
- `annet-orion`, прибитый к образу конкретного вендора.

На вопрос «какой контейнер должен выполнить команду для `core-rtr-1`?» нужно
отвечать *где-то*, и каждый раз. В Annet Oil на него отвечают в одном месте — в
роутере, управляемом простой JSON-картой:

```json
{
  "routes": {
    "router1.example.com":       "annet",
    "old-router.example.com":    "annet-telnet",
    "orion-device1.example.com": "annet-orion"
  }
}
```

Запрос называет хост; роутер резолвит его в контейнер; сервис annet делает
`docker exec` команды туда. Поскольку маршрутизация централизована и управляется
данными, добавить новый контейнер или переместить хост между контейнерами — это
правка конфига, а не кода. И поскольку это происходит *ниже* слоя интерфейсов, CLI,
API и агент получают идентичное поведение маршрутизации бесплатно.

## Решение №3: Docker Exec, а не SDK

Именно на это чаще всего возражают, поэтому скажу прямо.

Annet Oil управляет annet через **Docker Exec API** — по сути
`docker exec <container> annet <args>`, сделанный аккуратно через Docker SDK для
Go, — и парсит stdout/stderr. Он **не** подключает annet как библиотеку и не
общается с gRPC-сервером внутри контейнера.

Зачем отказываться от структурированных ответов ради парсинга текста?

**Что вы получаете:**

- **Ноль изменений в annet-контейнерах.** Они остаются стоковыми. Любая версия
  annet, любой кастомный билд работает в день выхода — никакой матрицы
  совместимости.
- **Реальная изоляция.** Каждый annet-контейнер — запечатанная коробка со своими
  зависимостями; границу обеспечивает Docker. Никакого общего Python-рантайма, ни
  запутанности версий между оркестратором и инструментом, который он оркестрирует.
- **Тривиальная расширяемость.** Новый вариант annet — это новый контейнер плюс
  одна строка в карте маршрутизации.
- **Достаточная производительность.** Латентность exec обычно <10 мс — пренебрежимо
  мало на фоне секунд, которые занимает реальный `diff` или `deploy` против
  устройства. Это система change-management'а, а не пожарный шланг телеметрии.

**Чем вы платите:**

- **Парсинг текста.** Вы читаете stdout/stderr, а не типизированную структуру.
  Хрупко, если формат вывода annet поедет.
- **Нет прогресса в реальном времени** для долгих операций — результат приходит,
  когда exec завершился.
- **Более грубая обработка ошибок**, чем дал бы структурированный API.

Альтернативы я рассматривал. Встроить Python-рантайм (или сайдкар на Python), чтобы
использовать SDK annet, — значит связать Annet Oil с внутренним API annet и
затащить языковой рантайм в Go-сервис. Добавить gRPC/REST-сервер *внутрь* каждого
annet-контейнера — раздуть образы и умножить число движущихся частей. Оба решают
проблемы, которых у меня пока нет.

Поэтому правило, на котором я остановился, явно проговаривает, *когда его
пересматривать*: уходить от Docker Exec стоит, только если у annet появится
официальный Go SDK, или если мне реально понадобится прогресс в реальном времени,
или если стабильная нагрузка перевалит за ~100 rps. Пока ни одно из этого не
случилось, скучный выбор — правильный. **Записать условия, которые перевернут
решение, — это то, что не даёт ему закостенеть в догму.**

## Ещё два края, которые стоит знать

**gNETcli для живых устройств.** `gen`/`diff`/`patch`/`deploy` идут через annet.
Но диагностика — show-команды, operational state — должна общаться с *устройством*,
а не с annet. Этот путь идёт через
[gNETcli](https://github.com/annetutil/gnetcli), и поэтому в диаграмме fan-out три
стрелки, а не одна.

**MCP крутится в контейнере, API — на хосте.** API нужен доступ к Docker-сокету,
чтобы делать exec в annet-контейнеры, поэтому он живёт на хосте. MCP-сервер
изолирован в собственном контейнере и достаёт API по HTTP
(`host.docker.internal:8080`). Агент получает изолированную минимальную
поверхность; привилегированный доступ к Docker остаётся на хосте, где ему и место.
Один общий токен аутентификации связывает обе стороны.

## Сквозная идея

Если и есть одна мысль, скрепляющая всю архитектуру, то вот она: **пропихни каждое
важное решение ниже слоя интерфейсов, сделай его один раз — и пусть все три двери
его унаследуют.** Маршрутизация, аутентификация, структурированные ошибки,
четырёхслойная форма фичи — ничто из этого не дублируется на каждый интерфейс.
Человек в CLI, CI-джоба по REST и AI-агент через MCP — все они просто вызывающие
одно охраняемое ядро.

Следующее в серии: **маршрутизация и инвентарь подробно** — как хостнейм резолвится
в контейнер *и* в набор кредов, и почему инвентарь — настоящий источник истины.
